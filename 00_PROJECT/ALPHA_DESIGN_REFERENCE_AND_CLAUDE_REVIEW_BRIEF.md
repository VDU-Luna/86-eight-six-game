# 1차 알파 통합 설계 참고서 및 Claude 자율 검토 지시서

상태: 독립 검토용 참고 문서  
작성 기준일: 2026-11-20  
목적: 현재까지의 프로젝트 방향과 합의된 설계를 한 문서에서 파악하고, Claude가 Roblox 플랫폼 제약과 게임성을 기준으로 알파 개발 설계를 독립적으로 검토·구체화하도록 전달  
중요: 이 문서는 기존 공식 문서를 대체하거나 수정하지 않는다. 모든 기획은 임시이며, 검토 결과는 사용자 검토 전까지 확정 사항이 아니다.

# PART A. 프로젝트 개요 및 검토 기준

## 1. 프로젝트 목표

- Roblox에서 개발하는 `86 -EIGHTY-SIX-` 세계관 기반의 온라인 액션 게임.
- 장기적으로 오픈월드, 스토리 캠페인, 별도 협동 PvE, PvP를 포함하는 확장형 Experience를 목표로 한다.
- 1차 알파는 모든 모드와 세계관 콘텐츠를 완성하는 버전이 아니다. 제한된 콘텐츠로 핵심 플레이 루프, 전투 조작감, 협동, 서버 안정성, 데이터 저장, 성능을 검증하는 버전이다.
- 기획 단계와 제작 단계를 분리한다. 사용자 승인 전까지 실제 Roblox Studio 구현, 모델링, 스크립팅을 시작하지 않는다.
- 모든 설정과 결정은 변경 가능하다. CONFIRMED는 현재 합의된 임시 기준이지 영구 고정이 아니다.

## 2. 1차 알파의 핵심 플레이 루프

메인 메뉴 → 오픈월드 진입 → Feldress 선택·탑승 → 이동·전투 → 임무/탐험 → 물자 획득 및 보급 → 기지 복귀·정비·업그레이드 → 다시 출격.

알파의 성공 기준은 콘텐츠의 양보다 아래 핵심이 실제로 재미있고 안정적으로 작동하는지 여부다.

1. Feldress를 조종하는 기본 이동과 전투가 명확하고 반응성이 좋다.
2. 일반 적과 특수 적의 구분, 전투 상황, 협동 플레이가 읽기 쉽다.
3. 전투 중 손상·부품 파괴·수리·보급이 의미 있는 선택을 만든다.
4. 월드에서 전투, 임무, 탐험, 거점 이용이 자연스럽게 연결된다.
5. 플레이어 수가 늘어도 서버 프레임, 네트워크, 물리, 메모리 부담이 통제된다.
6. 플레이어 계정 데이터와 서버별 월드 데이터가 올바르게 분리·저장된다.
7. PC와 모바일을 포함한 Roblox 이용 환경에서 핵심 조작이 가능하다.

## 3. 문서 우선순위와 이 문서의 역할

기존 저장소의 문서 체계는 다음과 같다.

- `00_PROJECT/MASTER_GDD.md`: 현재까지의 통합 기획 기준.
- `00_PROJECT/DECISIONS_LOG.md`: 결정과 변경의 시간순 이력. 과거 문장은 이후 정정에 의해 대체될 수 있다.
- `00_PROJECT/PLANNING_BACKLOG.md`: 미결정 항목과 현재 진행 상태.
- `00_PROJECT/ROADMAP.md`: 알파 범위와 개발 순서.
- `00_PROJECT/DEVELOPMENT_RULES.md`: 제작·문서 협업 원칙.
- 주제별 세계관, 스토리, 캐릭터, 게임플레이 문서: 해당 주제의 상세 자료.

이 문서는 위 문서들을 대체하지 않는 **Claude 검토용 통합 입력 자료**다. 내용이 충돌하면 기존 공식 문서의 최신 내용을 확인하고, 더 최근의 명시적 사용자 결정이 우선한다. 이 문서 자체도 누락이나 요약이 있을 수 있으므로, Claude는 작업 전 저장소의 최신 문서 전체를 읽어 교차 확인해야 한다.

## 4. 상태 표기

- CONFIRMED: 현재 사용자와 합의된 방향. 재검토 가능.
- PROPOSED: 기존 문서에서 제안한 방향이나 아직 확정되지 않은 항목.
- PENDING: 미결정.
- DEFERRED: 알파 이후로 보류.
- CLAUDE_RECOMMENDATION: Claude가 독립 검토 후 제안하는 내용. 사용자 승인 전까지 확정 아님.
- SUPERSEDED: 과거 결정이 이후 결정으로 대체됨.

Claude는 이 상태를 임의로 바꾸지 말고, 제안한 변경은 별도 변경 제안표에 기록해야 한다.

# PART B. 세계관과 플레이어 설정

## 5. 원작 세계관 적용 원칙

- 게임은 `86 -EIGHTY-SIX-`의 세계관을 기반으로 한다.
- 원작의 국가, 레기온, 펠드레스, 전쟁 배경과 기본 특성을 존중한다.
- 원작에 실제로 존재하는 설정과 게임을 위해 새로 만든 설정을 구분한다.
- 원작 인물과 주요 사건을 플레이어의 오리지널 서사 때문에 임의로 대체하거나 변경하지 않는다.
- 오픈월드 플레이어 부대는 원작 주요 인물들이 활동하는 전선과 구분된, 원작에서 상세히 묘사되지 않은 다른 활동 지역에서 작전을 수행한다.
- 원작의 정확한 연표에 세밀하게 종속되지 않는다.
- 업로드된 나무위키 PDF는 2차 정리 자료다. 공식 원작 자료와 동일한 권위를 가진 것으로 취급하지 않는다. 원작 세부 설정을 검증할 때는 공식 출처를 우선하고, 불확실하면 불확실하다고 표시한다.

## 6. 플레이어 캐릭터와 오픈월드 배경

- 플레이어는 산마그놀리아 공화국 출신 86 병사다.
- 공화국 중앙 군 지휘부로부터 레기온 지배 영역 깊숙이 진입하는 장기 특수 정찰 임무를 받았다. 사실상 소모성 임무라는 배경을 반영한다.
- 오픈월드 시작 시점에는 이미 레기온 지배 영역 심부에 진입한 상태다.
- 통신 및 지휘 체계 단절, 공화국 붕괴는 시작 상황을 설명하는 최소한의 배경으로 사용한다.
- 플레이어는 원작 주인공이 아닌 신규 오리지널 캐릭터다.
- 캐릭터 이름은 Roblox 표시 닉네임을 사용한다.
- 시작 시 별도 호출부호는 없으며, 계정 레벨 또는 업적을 통해 획득하는 방향이다.
- 개인 과거사를 직접 작성하는 복잡한 배경 생성기는 기본 설계에서 제외한다.
- 얼굴, 헤어, 피부색, 군복, 헬멧, 장구류 등 외형 커스터마이징을 제공한다.
- 캐릭터 외형과 군장 아이템은 전투 능력치에 영향을 주지 않는다.
- 원작 캐릭터는 오픈월드에서 NPC 역할을 수행할 수 있으나 알파에서 필수 구현 범위인지는 재검토한다.

## 7. 기지와 생존자 거점

- 플레이어 측은 버려진 과거 인류 군사 기지를 재활용해 본부로 사용한다.
- 인근에는 소수 생존자가 생활하는 별도의 안전 거점이 존재한다.
- 군사 기지는 작전, 정비, 보급, 장비 관리의 중심이고 생존자 거점은 거주와 보호의 역할을 담당한다.
- 기지 내부에는 사용 가능한 구역, 파손 구역, 미조사 구역이 공존한다.
- 미조사 구역에서는 과거 군사 시설, 병사·민간인의 흔적, 레기온 침입 및 전투 기록을 발견할 수 있다.
- 시설 복구는 필요한 물자 투입과 관련 임무 수행을 결합한다.
- 복구 시설은 기능 해금, 정찰 지원, 주변 월드 변화에 영향을 줄 수 있다.
- 복구한 시설은 레기온에게 재점령될 수 있으며, 시간·주변 전황·플레이어의 방어 및 작전 활동을 함께 고려한다.
- 알파에서는 제한된 검증 지역과 필수 시설만 선택한다. 대규모 대륙형 월드는 장기 확장 목표다.

# PART C. Experience 구조와 모드 범위

## 8. Roblox Experience 구조

- 하나의 Roblox Experience를 사용한다.
- 메인 메뉴는 공통 진입 Place다.
- 오픈월드, 스토리 캠페인, 별도 협동 PvE, PvP는 모드별 Place로 분리하는 방향이다.
- 각 모드는 독립된 세션·규칙·콘텐츠를 가질 수 있지만 공통 계정 데이터와 공유 시스템은 재사용한다.
- 계정 공통 데이터와 서버별 오픈월드 월드 상태는 분리한다.
- 오픈월드 서버마다 지역 점령, 기지 상태, 레기온 전황, 웨이브, 작전 진행이 독립적이다.
- 한 서버의 월드 진행이나 초기화가 다른 서버에 영향을 주지 않는다.
- 서버별 월드 사이클 초기화가 있더라도 계정 레벨, XP, 화폐, Feldress 소유 및 영구 업그레이드 등 계정 데이터는 유지하는 방향이다.
- 실제 Place 수, 텔레포트, 매칭, 재접속, 서버 종료 및 월드 복구 방식은 기술 설계에서 결정한다.

## 9. 모드별 장기 구상과 알파 범위

장기 모드:
1. Open World: 자유 탐험과 지속 전투, 임무, 기지 운영, 지역 확보.
2. Multiplayer PvE: 오픈월드에서 다루기 어려운 정밀하거나 대규모인 협동 임무.
3. PvP: 별도 공간에서 플레이어끼리 대전하는 FPS 스타일 콘텐츠.
4. Story Campaign: 원작 캐릭터를 직접 조작하는 캠페인. 초기 범위는 애니메이션 시즌 1·2 흐름을 우선 고려.

1차 알파:
- 오픈월드만 플레이 가능.
- 메인 메뉴에는 네 가지 모드를 표시하되, 알파에서는 Open World만 활성화.
- 나머지 모드는 '개발 중'으로 표시하고 진입을 막는다.
- 별도 PvE, PvP, 스토리 캠페인 상세 구현은 알파 이후.
- 대규모 오픈월드 전체가 아닌 제한된 검증 지역만 구현한다.

# PART D. 메인 메뉴, 정비, 창고

## 10. 메인 메뉴와 정비고 연출

- 메인 메뉴는 군사 정비고를 배경으로 하는 3D 화면이다.
- 카메라는 고정되어 있고 캐릭터는 이동하지 않는다.
- 정비 작업 구역은 주변보다 밝고, 정비고 전반은 비교적 어두운 군사 분위기다.
- 플레이어 캐릭터와 대표 Feldress 한 대를 정비 플랫폼에 배치한다.
- 다른 보유 Feldress를 배경에 모두 전시하지 않는다.
- 캐릭터는 Feldress의 대각선 앞쪽에 자연스럽게 서 있고 기본 대기 자세를 취한다.
- 카메라는 약간 낮은 시점으로 Feldress의 위압감을 표현한다.
- 좌측 세로 모드 카드: Story Campaign, Open World, Multiplayer Missions (PvE), PvP.
- 알파에서는 Open World만 활성화하고 나머지는 어둡게 처리한 뒤 '개발 중' 표시를 한다.
- 정확한 UI 위치, 카메라 거리/FOV, 간격, 프로필/재화 표시 등은 UI 단계에서 정한다.

## 11. 정비 화면과 창고

- 정비와 창고는 별도 Place가 아니라 공통 메인 Place 안의 전체 화면 전환이다.
- 정비 화면은 같은 정비고를 사용하며 카메라가 정비 플랫폼 쪽으로 가까워진다.
- 좌측 Feldress 목록에는 작은 이미지, 이름, 상태, 레벨을 표시한다.
- 중앙에는 선택된 Feldress의 3D 모델을 보여주고 마우스 드래그/터치로 회전해 살펴볼 수 있다.
- 정비 기능: 기체 선택, 부품 업그레이드, 무장 변경, 수리.
- 창고는 자원, 제작 재료, 설계도, 장비를 관리하는 별도 전체 화면이다.
- 세부 UI 배치는 구현 전 UX 설계에서 확정한다.

# PART E. Feldress 소유, 탑승, 하차, 파괴, 수리

## 12. Feldress 기본 소유와 출격

- 최초 지급 기체는 M1A4 Juggernaut 한 대다.
- 시작 무장은 주무장 후보 2종과 보조무장 후보 2종을 제공하고, 동시에 주무장 1개 + 보조무장 1개를 장착한다.
- Juggernaut의 추가 무장은 기본적으로 일반 게임 화폐로 해금한다.
- 다른 Feldress의 무장은 특성에 따라 일반 화폐+재료 또는 설계도/제작 구조를 적용할 수 있다.
- 플레이어는 여러 Feldress를 보유할 수 있으며 소유 수량에 고정 상한을 두지 않는 방향이다.
- 각 Feldress는 독립된 업그레이드와 장비 데이터를 가진다.
- 새로운 Feldress는 업그레이드 단계 0에서 시작한다.
- 기체 변경은 본부, 안전 거점 또는 허용된 전방 기지의 정비 시설에서 수행한다.
- 플레이어는 기지의 Feldress 스폰 지점에서 보유 기체 중 파괴되지 않은 기체를 선택해 스폰할 수 있다.

## 13. 탑승과 하차

- Feldress 가까이 접근해 상호작용 키를 눌러 탑승한다.
- 손상된 Feldress에는 탑승할 수 있다.
- 완전히 파괴된 Feldress에는 탑승할 수 없다.
- 하차 키를 누르면 현재 위치에서 즉시 내린다.
- 기본적으로 안전한 하차 지점을 찾거나 별도 출구 지점으로 이동하지 않는다.
- 하차 위치에 대한 기본 안전 판정도 두지 않는 방향이다.
- 하차 후 플레이어 캐릭터는 일반 3인칭 캐릭터 조작을 사용하고 환경과 상호작용할 수 있다.
- 탑승·하차 입력은 PC/모바일/컨트롤러별로 UX 단계에서 배정한다.

## 14. 무인 Feldress와 파티원 임시 사용

- 파일럿이 탑승하지 않은 Feldress는 원격 조종할 수 없다.
- 파일럿이 내리면 Feldress는 마지막 위치에 그대로 남는다.
- 소유자는 해당 Feldress의 다른 플레이어 탑승 허용 여부를 직접 설정할 수 있다.
- 탑승 허용 상태라면 같은 파티원은 소유자의 별도 승인 없이 탑승할 수 있다.
- 다른 파티의 플레이어는 탑승할 수 없다.
- 탑승한 파티원은 임시 조종자로서 해당 Feldress를 직접 조종하고 사용할 수 있다.
- 소유권, 기존 업그레이드, 장비 구성 및 영구 데이터는 원래 소유자에게 유지된다.
- 임시 사용자의 개인 Feldress 목록이나 장비 데이터는 변경되지 않는다.
- 임시 사용자가 자발적으로 하차하면 Feldress는 그 자리에 남고, 소유자 또는 같은 파티원이 다시 탑승할 수 있다.
- 원래 소유자는 임시 사용 중인 Feldress를 강제로 회수하는 별도 우선 탑승 기능을 필요로 하지 않는다. 필요하면 새 Feldress를 스폰하거나 탑승 허용 설정을 끌 수 있다.
- 임시 사용 중인 Feldress가 파괴되면 수리 비용은 원래 소유자가 부담한다.
- 파괴 상태는 기지에서 수리하며, 일반 심각 손상 수리보다 훨씬 높은 비용이 적용된다.
- 소유자가 다른 Feldress를 새로 스폰하면 기존 Feldress는 종류와 관계없이 즉시 사라진다. 임시 사용 중인 파티원이 있더라도 기존 기체와 탑승자는 제거되는 것으로 정리한다.
- 소유자가 게임을 나가거나 서버를 떠나면 소유 Feldress는 즉시 사라진다. 임시 탑승자가 있다면 함께 강제 하차·제거된다.
- 소유자 접속 종료 후 임시 사용자가 기체를 계속 보유하는 구조나 소유권 이전은 없다.

## 15. 파일럿이 Feldress 밖에서 전투 불능이 되는 경우

- 파일럿은 Feldress 밖에서 적에게 피해를 받을 수 있다.
- 파일럿은 Feldress와 별도의 체력을 가진다.
- 체력이 0이 되면 전투 불능 상태가 된다.
- 전투 불능 상태의 파일럿은 일정 시간 후 본부 또는 아군 기지에서 부활한다.
- 동료가 반드시 구조해야만 부활하는 구조는 아니다.
- 파일럿이 Feldress 안팎에서 전투 불능이 되어도 Feldress가 파괴되지 않았다면 해당 기체는 마지막 위치에 남는다.
- 부활 후 기지의 Feldress 스폰 지점에서 보유한 비파괴 Feldress 중 하나를 직접 선택한다.
- 마지막 사용 기체를 자동 선택하지 않는다.
- 선택한 기체가 스폰된 뒤 플레이어는 탑승 상태가 아닌 파일럿 상태로 등장하고, 직접 걸어가 상호작용 키로 탑승한다.
- 플레이어가 새 기체를 스폰하면 이전에 남아 있던 자기 Feldress는 제거된다.

## 16. Feldress 정비와 수리

### 손상과 자동 회복
- 경미한 손상은 시간에 따라 자동 회복한다.
- 전투 중에는 느리게, 전투 외 상황에서는 일반 속도로, 본부 또는 플레이어가 점령한 기지에서는 빠르게 회복하는 방향이다.
- 심각한 손상은 비용을 지불하는 정비 수리가 필요하다.
- 심각 손상 수리는 비용 지불 후 즉시 완료하는 방향이다.
- 파괴 상태는 기지에서 직접 수리할 수 있으며 일반 심각 손상보다 훨씬 비싸다.

### 부품별 손상
- Feldress는 전체 체력 하나만이 아니라 부품별 손상과 파괴 상태를 가진다.
- 후보 부품 범주: 다리/이동부, 주무장, 보조무장, 장갑, 엔진, 센서, 제어 장치, 특수 장비.
- 기체 구조에 따라 다리 그룹 수와 구성이 달라질 수 있다.
- 부품은 손상 누적에 따라 성능이 점진적으로 저하되고, 완전 파괴 시 해당 기능을 상실한다.
- HUD 손상 상태는 정상(초록), 경미(노랑), 심각(주황), 파괴(빨강) 네 단계다.
- 장갑은 부위별로 별도 관리한다. 공격은 우선 장갑에 적용되며 장갑이 파괴되기 전에는 내부 부품이 보호된다. 장갑을 파괴한 공격의 초과 피해는 같은 공격에서 내부 부품으로 넘어간다.
- 직접 공격은 명중한 내부 부품에 집중되는 방향이고, 폭발/AOE는 여러 내부 부품에 분배하는 규칙을 사용한다.
- 부품별 방어/저항 값을 두는 것을 기본으로 하고, 구현 여력이 있으면 공격 유형과 상호작용시킨다.
- 부품 간 연쇄 효과는 직접 연결된 부품의 기능 저하까지만 적용하며 무한 재귀 피해는 적용하지 않는다.
- 부품별 내구도, 방어값, 피해 분배 수치, 연결 관계는 미정이다.

### 필드 수리
- 파일럿이 Feldress에서 내려 직접 수리한다.
- 수리 중 Feldress는 전투 행동을 할 수 없다.
- 수리 중인 파일럿도 이동할 수 없다. 이동하려면 수리를 중단해야 하며 진행도는 초기화된다.
- 약한 공격은 수리를 중단시키지 않지만 강한 공격은 즉시 중단시킨다.
- 중단되면 수리 진행도는 처음부터 다시 시작한다.
- 이미 소비된 재료는 반환하지 않는다.
- 파일럿에게 기본 보호막이나 무적을 제공하지 않는다. 수리 중 파일럿은 공격에 노출된다.
- 수리 중인 Feldress는 일반적인 피해를 그대로 받으며 피해 감소나 무적을 얻지 않는다.
- 다른 플레이어는 자유롭게 수리 중인 파일럿을 보호할 수 있다.
- 기본 수리 도구는 재사용 장비, 일반 수리 재료는 필요량만큼 소비, 특수 수리 키트는 특정 부품/장비 전용 소모품으로 구분한다.
- 일반 부품은 필드에서 완전 수리 가능하다. 특수 장비 또는 심각 손상 부품은 필드에서 부분 수리만 허용될 수 있다.
- 엔진과 제어 장치는 본부/아군 점령 기지에서만 수리한다.
- 다리/이동 부품은 필드 수리를 허용한다.
- 외부 장갑, 주무장, 보조무장, 센서, 다리/이동부는 필드 및 기지 수리 대상. 특수 장비는 장비별로 정한다.

## 17. Feldress 업그레이드

- 업그레이드 부위는 장갑, 엔진, 무장, 센서, 특수 장비의 5개 분야다.
- 각 분야는 독립적으로 업그레이드한다.
- 기체 레벨은 업그레이드 최대 단계 제한을 해금하는 역할을 하며, 레벨 1당 업그레이드 1단계처럼 일대일로 연결하지 않는다.
- 각 기체는 최종 업그레이드 단계가 다를 수 있다.
- 같은 기체 안에서는 5개 분야가 동일한 최종 최대 단계에 도달할 수 있다.
- 분야별 비용과 재료는 다르다.
- 비용은 공통 화폐와 분야별 재료를 사용한다.
- 업그레이드 실패는 없고 성공 시에만 자원을 소비한다.
- 업그레이드는 영구 적용되며 다운그레이드/초기화 기능은 기본 설계에 없다.
- 기체별 업그레이드는 독립적이며 다른 기체로 이전되지 않는다.

# PART F. 카메라, HUD, 이동과 기동

## 18. 카메라

- 기본 전투 시점은 1인칭 콕핏 시점이다.
- 선택형 3인칭은 Feldress 뒤쪽에서 보는 후방 시점이다.
- 두 시점은 플레이어가 토글로 전환한다.
- 3인칭 카메라는 중간 거리에서 기체와 전장을 함께 볼 수 있게 한다.
- 기본적으로 Feldress 뒤를 자동 추적한다.
- 마우스 오른쪽 버튼을 누른 상태에서 마우스를 움직이면 자유 회전한다.
- 버튼을 놓으면 후방 추적 시점으로 돌아온다.
- 카메라 회전은 기체 이동/방향 조작과 분리한다.
- 1인칭은 기본적으로 외부 전장 시야에 집중하며 콕핏 내부 모델/프레임을 표시하지 않는다.
- 설정에서 콕핏 내부 표시를 별도로 켜고 끌 수 있다. 이는 카메라 시점을 바꾸지 않는다.
- 1인칭 HUD에는 부위 실루엣과 손상 상태를 표시한다.
- 3인칭에는 부위 손상 HUD를 표시하지 않으며, 필요하면 1인칭으로 전환해 확인한다.

## 19. HUD와 피격 피드백

- 부위 실루엣의 각 부위를 색상으로 표시한다.
- 초록=정상, 노랑=경미 손상, 주황=심각 손상, 빨강=파괴.
- 별도 전체 HP 게이지나 전체 상태 숫자는 표시하지 않는 방향이다.
- HUD는 간결하게 유지한다.
- 피격 시 짧은 화면 흔들림과 화면 가장자리의 은은한 붉은 빛을 사용한다.
- 모든 작은 타격마다 과도한 효과를 내지 않고 일정 임계값 이상의 피격에 반응한다.
- 연속 피격은 효과를 무한 중첩하지 않고 병합/억제한다.
- 화면 흔들림은 방향에 따라 달라지지 않는 짧은 공통 효과다.
- 1인칭과 3인칭 모두에 적용한다.
- 부품 파괴 시 일반 피격보다 강한 효과를 주고, HUD에서 해당 부위를 잠깐 깜빡인다. 이후 빨강 상태로 유지한다.
- 별도 방향 표시기나 텍스트 경고는 기본적으로 사용하지 않는다.

## 20. 기본 이동

- WASD 기반의 표준 3D 액션 조작.
- 마우스 방향에 따라 기체가 회전한다.
- 좌우 스트레이프가 가능하며 측면 입력만으로 기체가 강제로 회전하지 않는다.
- 후진 성능은 Feldress 종류에 따라 다를 수 있다.
- 회전 속도와 이동 관성은 기체 종류/중량에 따라 차이를 둔다. 경량 기체는 빠르고 중량 기체는 묵직한 방향.
- 모든 Feldress는 점프할 수 있으나 성능은 기체마다 다를 수 있다.
- 공중에서 회전 가능하지만 방향 전환은 관성의 영향을 받는다. 기본 갈고리 및 특수 장비로 공중 방향 전환을 보조할 수 있다.
- 달리기는 에너지를 소비하며 에너지가 0이 되면 일반 이동으로 자동 전환되고 자동으로 달리기를 재개하지 않는다.

## 21. 갈고리 시스템

- 화면 중앙 조준점이 가리키는 방향으로 발사한다. 자동 타깃 선택이나 부착 가능 여부 표시기는 없다.
- 좌·우 두 개를 독립적으로 사용할 수 있다.
- 양쪽 버튼을 함께 누르면 동시에 발사할 수 있다.
- 각 갈고리는 발사부터 이동, 매달림까지 버튼을 계속 누르고 있어야 유지된다. 버튼을 놓으면 해당 갈고리만 즉시 해제된다.
- 갈고리는 지상과 공중에서 모두 사용할 수 있다.
- 지형, 구조물, 이동 물체, 레기온 등 대부분의 대상에 부착할 수 있다.
- 조준선상 여러 대상이 겹치면 가장 앞/가까운 대상이 우선이다. 그 대상이 부착 불가이거나 최대 사거리 밖이면 뒤의 대상에 관통 부착하지 않고 발사 실패한다.
- 발사체는 눈에 보이며 기본 발사 속도는 모든 Feldress 공통이다.
- 연결되면 기본적으로 부착 지점 방향으로 끌려간다. 이동 중 방향 수정은 제한되고 수동 가속/감속은 불가능하다.
- 부착 지점에 도달하면 연결을 유지한 채 자동으로 매달림 상태로 전환한다.
- 매달림 중 일시 정지 가능. 연결에는 최대 유지 시간이 있으며 자동 해제된다.
- 두 갈고리를 동시에 연결하면 두 지점 사이 균형을 잡고, 입력이 없으면 장력과 기존 관성에 따라 위치가 정해진다. 이동 입력은 방향 이동을 허용한다.
- 매달림 중 카메라 회전과 제한된 위치 조정이 가능하나 일반 자유 이동은 불가능하다.
- 매달림 중 공격 가능 무기는 무기 유형에 따라 제한한다. 허용 무기는 지상과 동일한 공격 성능을 유지한다. 재장전 및 주/보조 무장 조작 가능.
- 회피 동작은 모든 연결 갈고리를 해제한다.
- 갈고리 이동 중에는 갈고리 호환 무기로 공격할 수 있다.
- 갈고리 연결은 에너지를 지속 소비하며 정지 상태에서도 소모한다. 에너지가 0이면 연결이 해제되고 기존 관성이 이어진다.
- 갈고리 해제 후 짧은 재사용 대기시간이 있다.
- 최대 사거리는 Feldress와 부착점 사이 직선거리 기준이다. 기본 최대 사거리는 모든 Feldress 공통이며 특수 장비/업그레이드로 확장할 수 있다.
- 최대 사거리를 넘으면 즉시 연결이 해제된다.
- 갈고리 줄이 지형/건물/이동 장애물에 막히면 발사 실패 또는 연결 해제한다. 다른 Feldress와 레기온, 그들의 갈고리 줄은 장애물 판정에서 제외한다.
- 연결 성공 피드백은 짧은 금속성 클릭 소리를 기본으로 한다. 연결 지점 표식이나 추가 UI 아이콘은 두지 않고 연결된 줄 자체를 표시한다.
- 줄의 휘어짐/장력/흔들림은 물리적으로 표현하되 Roblox 성능 검증 후 단순화할 수 있다.
- 강한 충격, 피격 부위, 대상 상태에 따라 연결이 끊길 수 있다. 일반 사용이나 약한 피격만으로 갈고리 자체가 파손되지는 않는다.
- 갈고리 장치가 파손되면 수리 전까지 해당 갈고리를 사용할 수 없다. 필드 수리는 제한된 전용 도구, 기지 수리는 정상 정비로 처리한다.
- 양쪽 갈고리는 독립 상태로 관리한다. 한쪽 파손/해제는 다른 쪽에 자동 영향을 주지 않는다.

## 22. 대시

- 모든 Feldress는 기본 대시를 가진다.
- 대시는 기체가 바라보는 방향의 정면으로만 진행하며 WASD 방향과 무관하다.
- 지상과 공중 대시를 모두 지원하되 성능/제약 차이는 후속 밸런스에서 정한다.
- 대시 중 방향 조정이나 회전은 불가능하다.
- 무기 유형에 따라 대시 중 공격 가능 여부가 달라진다.
- 피격되어도 대시는 중단되지 않는다.
- 갈고리 연결 중 대시를 시작하면 모든 연결 갈고리를 즉시 해제한다.
- 대시 종료 후 쿨다운이 시작된다. 지상/공중 대시는 하나의 쿨다운을 공유한다.
- 대시는 기존 이동 관성을 무시하고 전용 대시 속도를 사용한다.
- 대시 종료 시 감속 과정 없이 일반 이동으로 즉시 복귀한다.
- 벽/통과 불가 장애물 또는 적 레기온과 충돌하면 즉시 종료한다.
- 아군 Feldress는 통과할 수 있고 대시 종료 충돌로 처리하지 않는다.
- 대시와 연관된 핵심 부품이 완전히 파괴되면 대시를 사용할 수 없다. 경미/심각 손상만으로는 비활성화하지 않는다.
- 사용 불가 상태에서 입력하면 짧은 경고음만 재생한다. 쿨다운 중 입력은 무시하고 별도 피드백이나 입력 예약은 없다.
- 대시 거리/속도/시간/쿨다운, 지상·공중 차이, 무기 호환, 비활성화 부품 목록은 미정이다.

# PART G. 전투, 무장, 탄약, 에너지

## 23. 무장 운용 기본 구조

- 주무장과 보조무장은 독립적으로 장착되는 무기다. 한 슬롯에서 다른 무기로 즉시 교체하는 구조가 아니다.
- 주무장과 보조무장은 각각 별도 공격 입력을 가진다.
- 두 무장은 동시에 발사할 수 있다.
- 각 무장은 탄창과 재장전 상태를 독립적으로 관리한다.
- 한쪽 무장을 재장전하는 동안 다른 무장은 발사할 수 있다.
- 두 무장을 동시에 재장전할 수 있다. 이때 두 무장 모두 발사할 수 없지만 이동과 점프는 가능하다.
- 강한 피격으로 재장전이 중단되면 영향을 받은 무장만 중단되고 다른 무장은 계속 재장전한다.
- 재장전 중단 시 진행도는 초기화되고 처음부터 다시 시작한다.
- 재장전 완료 전에는 예비 탄약을 소비하지 않는다.
- 약한 피격은 재장전을 유지하지만 강한 피격은 중단한다. 강한 피격 임계값과 어느 부위가 어느 무장에 영향을 주는지는 미정이다.

## 24. 조준과 발사 방식

- 무기별 혼합 조준 방식을 사용한다.
- 일반 사격 무기는 화면 조준점을 기준으로 자유 조준한다.
- 유도 무기와 일부 특수 무기는 타깃 지정/추적을 사용할 수 있다.
- 발사 방식은 무기 특성에 따라 단발, 자동 연사, 점사, 충전, 지속 발사 등을 사용한다.
- 서로 다른 무기라도 공통 발사 처리 프레임워크를 재사용해 유지보수와 연산량을 줄인다.
- 공통 공격 버튼을 기본으로 하되 무기 특성에 따라 누름/홀드/릴리즈 동작을 구분한다.
- 구체 무기 목록, 탄속, 발사 간격, 탄창, 반동, 유도 방식, 공격 입력 매핑은 미정이다.

## 25. 탄약과 재장전

- 탄약은 하나의 통합 탄약이 아니라 종류별로 구분한다.
- 같은 탄약 종류를 사용하는 호환 무기는 공용 예비 탄약 보유량을 공유한다.
- 무기별 탄창 용량은 독립적이다.
- 재장전은 해당 무기 탄창을 같은 종류의 공용 예비 탄약에서 보충한다.
- 수동 재장전을 허용하고 탄창이 비면 예비 탄약이 있을 때 자동 재장전을 시도한다.
- 예비 탄약이 없으면 재장전할 수 없다.
- 재장전 중 이동과 점프는 허용한다.
- 재장전 중 공격, 대시, 갈고리는 제한한다.
- 무기별 재장전 시간, 탄창 크기, 탄약 종류, 예비 탄약 상한은 미정이다.

## 26. 보급

- 기본 탄약은 본부/보급 시설에서 무료 보충한다.
- 특수 탄약은 자원을 지불하고 보충한다.
- 기본 보급은 기지 중심이다.
- 일부 임무에는 현장 보급 차량이 등장할 수 있다.
- 현장 보급 차량은 기본 탄약과 특수 탄약을 모두 보급할 수 있다.
- 기본 탄약 무료, 특수 탄약 유료 규칙은 차량에도 동일 적용한다.
- 차량 재고는 기본적으로 차량 전체가 공유하는 공용 총량으로 관리한다.
- 일부 지정 품목만 별도 품목별 보급 횟수/개별 한도를 둘 수 있다.
- 개별 제한 품목, 공용 총량 단위/수치, 차감량, 재고 초기화 및 보충 조건은 미정이다.

## 27. 에너지

에너지는 무기 탄약이 아니라 Feldress 기동 자원이다.

에너지 소비:
- 달리기
- 점프 발동 시 1회 소비
- 대시 중 지속 소비
- 갈고리 연결 유지 중 지속 소비(정지 상태 포함)

회복:
- 에너지 소비 행동을 멈춘 뒤 짧은 대기시간 후 자동 회복한다.
- 회복 중 소비 행동을 다시 시작하면 회복이 중단되고 대기시간이 다시 시작된다.
- 피격은 에너지 회복을 중단시키지 않는다.
- 전투 중/전투 외/기지 등 장소에 따른 회복 속도 차이는 없다.

에너지 0:
- 일반 이동과 기본 전투는 가능하다.
- 달리기, 점프, 대시, 갈고리는 사용할 수 없다.
- 별도의 피로 상태나 기본 이동 속도 페널티는 없다.
- 달리기 도중 에너지가 0이 되면 일반 이동으로 전환하고, 에너지가 회복되어도 자동으로 달리기를 재개하지 않는다.
- 갈고리 연결 중 에너지가 0이 되면 연결이 해제되고 기존 관성이 이어진다.

점프:
- 버튼을 누르고 있는 동안 차징하고, 버튼을 놓으면 점프한다.
- 차징 시간에 따라 점프 높이가 정해지고 최대 차징 시간이 지나면 더 높아지지 않는다.
- 차징 중 에너지를 소비하지 않는다.
- 차징은 취소할 수 없고 피격으로 중단되지 않는다. 버튼을 놓으면 점프가 실행된다.
- 에너지가 부족하면 차징을 시작할 수 없다.
- 에너지는 실제 점프 발동 시 고정량을 한 번 소비하며 공중에서 추가 소비하지 않는다.

미정:
- 최대 에너지, 달리기/대시/갈고리 소비율, 점프 소비량, 회복 대기시간과 속도, 차징 시간/높이 곡선, 양쪽 갈고리 동시 연결 시 소비량.

# PART H. 피해, 파괴, Legion

## 28. Feldress 피해 판정

- 직접 공격은 실제 명중 위치에 따라 맞은 부위를 선택한다.
- 폭발/AOE는 정해진 분배 규칙을 사용한다.
- 판정이 불명확하거나 해결할 수 없는 경우 단순화된 부위 선택 규칙을 사용한다.
- 장갑은 부위별로 독립 내구도를 가진다.
- 공격은 장갑에 먼저 적용되고, 장갑이 남아 있는 동안 내부 부품은 보호된다.
- 한 번의 공격으로 장갑이 파괴되면 초과 피해가 같은 공격에서 내부 부품에 전달된다.
- 일반/직접 공격은 명중한 내부 부품에 집중하고 폭발/AOE는 여러 내부 부품에 분배한다.
- 부품별 방어/저항 값을 기본으로 사용한다. 구현 여력이 있으면 공격 유형별 상호작용을 추가한다.
- 각 내부 부품은 독립 내구도와 손상 단계를 가진다.
- 손상은 기능/성능을 점진적으로 저하시키고 파괴 시 해당 기능을 잃는다.
- 부품 간 연결 효과는 직접 연결된 부품의 기능 저하까지만 전달한다. 연쇄 내구도 피해나 무한 재귀 효과는 없다.
- 실제 수치, AOE 분배 비율, 부위 선택 예외, 부품 연결 그래프는 미정이다.

## 29. Legion 원작 특성 및 게임용 분류

- 원작에 존재하는 Legion 종류와 기본 특징을 존중한다.
- 원작 분류와 게임에서 부여하는 전투 역할을 분리해서 문서화한다.
- 일반 Legion은 개체별 세밀한 부위 파괴보다 단순화된 피해 시스템을 사용한다.
- 일반 Legion 부품 기능 범주는 기동, 무장, 장갑, 코어 등을 기준으로 하되 기체 구조에 따라 실제 부품은 다를 수 있다.
- 일반 Legion의 손상 단계는 정상 → 손상 → 파괴의 3단계다.
- 손상은 성능 저하, 파괴는 해당 기능 상실을 뜻한다.
- 일반 Legion은 전투가 끝나거나 교전에서 벗어난 뒤 일정 시간 후 손상/파괴 부품을 자동 회복할 수 있다. 전투 중에는 자동 회복하지 않는다.
- Open World 일반 Legion과 지휘관급 Legion은 간소화된 3단계 시스템을 사용한다.
- 오픈월드 최종 임무 보스와 향후 별도 PvE의 보스/지휘관급은 상세 부위 피해를 사용할 수 있다.
- 원거리 Legion은 개별 부위 피해 계산을 생략하거나 추상 전황으로 처리한다.

## 30. Legion 출현과 AI 기본 방향

- 평상시 지속 출현 + 조건부 대규모 웨이브의 혼합 구조.
- 웨이브 발동은 시간 경과, 플레이어 활동, 임무 진행 조건을 결합한다.
- 웨이브 규모와 난이도는 플레이어 수, 활동 상황, 임무 난이도에 적응하는 방향이다.
- 지역별 기본 출현 종류를 두고 임무/전투 상황에 따라 특수 Legion을 추가한다.
- 지휘관급 Legion은 일반 지역에서 낮은 확률, 웨이브/특수 작전에서 조건에 따라 확정 등장, 일부 중요 지역에서는 상시 배치 가능.
- 원작 지휘관급과 게임 오리지널 개체를 함께 활용하되 오리지널 설정은 명확히 구분한다.
- 지휘관은 주변 Legion의 행동과 전투 양상에 영향을 줄 수 있다.
- 지휘관 제거 시 지휘 효과를 해제하고 일반 Legion은 기본 행동을 유지한다. 일부만 짧은 혼란 상태를 보일 수 있다.
- 지휘권 승계는 조건을 만족하는 다른 지휘관이 이미 존재할 때만 수행한다. 새 지휘관을 자동 생성하지 않는다.
- 최적화 방향: 월드 AI 관리자, 소수 지휘관 AI, 경량 일반 AI, 특수 AI 계층으로 분리한다.
- 거리와 전투 중요도에 따라 AI 활성화 수준과 갱신 빈도를 낮춘다.
- 원거리 개체는 상세 AI 대신 추상 전황으로 관리할 수 있다.
- 모든 적에게 복잡한 독립 AI를 적용하지 않는다.
- 실제 병종, 스폰 밀도, 동시 활성 개체 수, AI 주기, 지휘 효과, 공격/감지 규칙은 미정이다.

# PART I. 플레이어 성장과 경제

## 31. 계정 성장

- 모든 모드에서 공유하는 계정 공통 레벨을 사용한다.
- 레벨은 Feldress 업그레이드 단계 상한, 장비/기능 해금, 일부 임무 요구 조건, 보상에 영향을 준다.
- 레벨 자체가 전투 능력치를 직접 올리는 구조는 사용하지 않는다.
- XP는 일반 화폐와 분리한다.
- XP 획득 경로 후보: 임무 완료, 전투 기여, 탐험.
- 군 계급은 일반 성장 시스템의 핵심으로 사용하지 않고 스토리/특정 임무에서 제한적으로 사용할 수 있다.
- 계급 명칭/승급, XP 곡선, 성장 수치, 신규/복귀 플레이어 격차는 미정이다.

## 32. 화폐와 제작

- 공통 화폐는 일반 화폐와 프리미엄 화폐 두 종류를 구상한다.
- XP는 화폐와 별도다.
- 제작 재료는 별도 수집한다.
- Feldress 설계도는 기체 제작 해금에 사용한다.

## Claude 자율 알파 설계 검토 프롬프트

너는 Roblox 플랫폼을 깊이 이해하는 시니어 게임 디렉터, 시스템 디자이너, 네트워크/서버 아키텍트, 최적화 엔지니어, UX 디자이너의 관점으로 이 프로젝트의 1차 알파 설계를 독립적으로 완성해야 한다.

### 1. 임무

이 프로젝트의 목표는 `86 -EIGHTY-SIX-` 세계관 기반 Roblox 온라인 액션 게임의 1차 알파를 설계하는 것이다. 제공된 통합 참고 문서와 GitHub 저장소의 최신 공식 문서를 모두 읽고, 현재까지의 기획을 Roblox의 실제 기술적 한계, 개발 규모, 플레이 재미, 멀티플레이 안정성, 유지보수 가능성을 기준으로 검토하라.

**사용자에게 기획 선택을 질문하지 마라.** 미정 항목은 네가 직접 분석하고 가장 합리적인 안을 선택하라. 여러 선택지가 있더라도 최선의 안을 결정하고, 대안과 선택 이유를 문서에 남겨라. 필수 정보가 부족해도 질문으로 작업을 멈추지 말고, 명시적인 가정과 위험을 기록한 뒤 설계를 진행하라.

### 2. 자율 결정 권한

- 현재 확정된 기획도 절대 변경 불가한 규칙으로 취급하지 마라.
- Roblox에서 구현이 지나치게 어렵거나, 성능·네트워크·조작감·재미·유지보수 측면에서 더 나은 대안이 있다면 기존 결정을 수정하는 것을 제안할 수 있다.
- 단, 기존 결정과 변경 제안을 섞어 기록하지 마라. 각 변경은 반드시 기존 결정, 문제점/근거, 대체안, 기대 효과, 비용/부작용, 마이그레이션 영향을 표로 정리하라.
- 변경은 어디까지나 Claude의 독립 제안이다. 사용자 승인 전에는 공식 기획이 변경된 것으로 간주하지 마라.
- 알파 범위에 필요하지 않은 장기 기능은 과감히 제외하거나 이후 단계로 미뤄라.
- Roblox에서 가능한 것처럼 보이더라도 서버 성능이나 실제 기기에서 검증되지 않은 기능을 무조건 채택하지 마라.
- 복잡한 시스템을 선택할 때는 그 복잡성이 플레이어에게 주는 구체적인 재미가 구현·운영 비용을 정당화하는지 판단하라.

### 3. 저장소 보호 및 파일 분리 규칙 — 반드시 준수

1. 작업을 시작할 때 GitHub 저장소의 최신 `main` 브랜치와 다음 문서를 포함한 관련 문서를 전부 확인하라.
   - `MASTER_GDD.md`
   - `DECISIONS_LOG.md`
   - `PLANNING_BACKLOG.md`
   - `ROADMAP.md`
   - `DEVELOPMENT_RULES.md`
   - 세계관/스토리/캐릭터/게임플레이 관련 문서
2. 이 참고 문서는 입력 자료일 뿐이며, 기존 문서는 읽기 전용으로 취급하라.
3. **기존 문서를 직접 수정·삭제·이동·이름 변경하지 마라.** 기존 데이터와 검토 결과를 혼합하지 마라.
4. 검토 결과는 별도의 새 폴더에 작성하라. 권장 경로:
   `CLAUDE_ALPHA_REVIEW/`
5. 검토 결과를 하나의 거대한 문서로 몰아넣지 말고, 아래 주제별 Markdown 파일로 분리하라.
6. 파일이 이미 존재한다면 덮어쓰지 말고 새 버전 또는 날짜가 포함된 하위 폴더를 만들어라.
7. 코드, Roblox Studio 프로젝트, 모델, 스크립트는 생성하거나 수정하지 마라. 이번 임무는 기획·아키텍처·검토 문서 작성이다.
8. GitHub에 쓸 권한이 없다면 로컬 작업 공간에 동일한 폴더 구조로 작성하고, 저장소에 반영하지 못했다는 사실을 최종 보고하라.
9. 커밋이 가능하다면 새 검토 문서만 커밋하라. 기존 공식 문서 변경이 포함되지 않았는지 커밋 diff를 확인하라.

### 5. Roblox 플랫폼 조사 요구

- 최신 Roblox Creator Documentation을 직접 확인하라. 기억에 의존해 API 동작이나 제한을 단정하지 마라.
- 관련 공식 문서의 제목, URL, 확인 날짜를 기록하라.
- 특히 다음 주제를 확인하라.
  - 서버/클라이언트 실행 모델과 네트워크 소유권
  - RemoteEvent/RemoteFunction 및 서버 검증
  - 물리 시뮬레이션과 네트워크 복제
  - StreamingEnabled 및 Instance streaming
  - DataStoreService 및 저장 요청 제한/실패 처리
  - MemoryStoreService가 적합한 경우와 사용 제한
  - TeleportService와 Place 간 이동/실패 처리
  - 서버 종료 알림 및 데이터 저장 보장 전략
  - MicroProfiler, Developer Console, 서버 성능 측정 도구
  - 모바일 기기 성능과 입력/UI 제약
- 공식 문서로 확인한 사실, 설계상 추론, 네가 제안하는 정책을 구분하라.
- 확인되지 않은 API 한계나 숫자를 만들어내지 마라. 확인 불가능한 것은 `검증 필요`로 표시하라.

### 6. 설계 품질 기준

각 시스템은 아래 질문에 답할 수 있어야 한다.

1. 플레이어가 실제로 무엇을 하고 어떤 재미를 얻는가?
2. 핵심 상태와 상태 전이는 무엇인가?
3. 서버가 권위 있게 판단해야 할 데이터는 무엇인가?
4. 클라이언트에서 연출/예측해도 되는 것은 무엇인가?
5. 한 플레이어와 최대 목표 인원에서 비용이 어떻게 증가하는가?
6. 네트워크 지연이나 플레이어 이탈 시 어떻게 복구되는가?
7. 악용이나 비정상 입력을 어떻게 막는가?
8. 알파에서 꼭 필요한가, 이후 버전으로 미뤄도 되는가?
9. 실패/예외 상황과 플레이어 피드백은 무엇인가?
10. 테스트를 통해 성공 여부를 어떻게 측정하는가?

### 7. 수치 결정 원칙

- 필요한 수치가 있다면 네가 권장 초기값 또는 테스트 범위를 제안하라.
- 임의의 숫자를 확정 사실처럼 표현하지 말고, `초기 가설`, `프로토타입 시작값`, `측정 후 조정`으로 표시하라.
- 수치마다 플레이 감각, 성능, 밸런스에 미치는 이유를 설명하라.
- 알파에서 검증할 수 없는 장기 밸런스 수치를 과도하게 세밀화하지 마라.
- Roblox의 공식 플랫폼 제한과 게임 내 튜닝 값을 혼동하지 마라.

### 8. 범위 통제

- 알파는 제한된 검증 지역과 최소 병종, 최소 무기, 최소 임무로 핵심 루프를 완성한다.
- 모든 원작 기체/Legion, 거대한 세계, 장기 캠페인, PvP, 별도 PvE를 알파에 억지로 넣지 마라.
- 고비용 시스템은 재미를 유지하는 가장 단순한 형태로 대체할 수 있다.
- 미래 확장성을 고려하되, 미래 기능을 위해 알파를 과도하게 복잡하게 만들지 마라.
- 구현되지 않은 기능을 문서상 이미 구현된 것처럼 표현하지 마라.

### 9. 결과물 작성 방식

- 문서는 한국어로 작성하라. Roblox API/서비스/클래스명과 업계 표준 용어는 원문 병기 가능.
- 각 문서는 개요, 권장 결정, 근거, 상태/예외, 성능 영향, 미정/검증 항목을 포함하라.
- 결정에는 `KEEP`, `CHANGE`, `DEFER`, `REMOVE`, `NEW` 라벨을 붙여라.
- 제안과 기존 합의를 시각적으로 명확히 구분하라.
- 문서 간 용어와 수치가 서로 충돌하지 않도록 교차 검토하라.
- 각 문서 상단에 작성일, 문서 버전, 검토 기준 저장소 커밋/브랜치를 기록하라.
- 모든 외부 근거에는 링크와 확인 날짜를 붙여라.
- 불확실성을 숨기지 말고 가정과 검증 계획을 기록하라.

### 10. 최종 보고

작업을 마친 뒤 다음을 요약하라.

1. 생성한 파일 전체 목록과 각 파일의 목적.
2. 알파 설계의 핵심 권장 결정.
3. 기존 기획에서 변경을 권고한 가장 중요한 항목.
4. Roblox 공식 문서로 확인한 주요 제약.
5. 알파에서 반드시 검증해야 할 기술적 위험.
6. 기존 파일을 수정하지 않았다는 확인.
7. 코드/모델/Studio 구현은 시작하지 않았다는 확인.
8. 사용자에게 승인받아야 할 변경 제안 목록.

다시 강조한다. **사용자에게 질문을 던지며 기획을 진행하지 말고, 네가 독립적으로 판단해 완성도 높은 검토 문서를 작성하라.** 기존 결정을 변경할 수 있지만 기존 자료와 섞지 말고 별도 파일에 제안으로 기록하라. 최종 결정권은 사용자에게 있다.

# PART L. 사용자 검토용 체크포인트

Claude의 결과를 검토할 때는 특히 아래를 확인한다.

- 기존에 합의한 재미 요소를 불필요하게 삭제하지 않았는가?
- Roblox에서 구현할 수 없는 수준의 물리/AI/네트워크 복잡성을 제안하지 않았는가?
- 성능을 위해 게임성이 지나치게 훼손되지는 않았는가?
- 서버 권한과 데이터 저장이 안전한가?
- 모바일 플레이가 사실상 불가능해지지 않는가?
- 알파 범위가 과도하게 커지지 않았는가?
- 기존 기획을 바꾸는 이유와 영향이 명확한가?
- 제안이 기존 공식 문서에 무단 반영되지 않았는가?

**최종 원칙:** Claude의 문서는 독립적인 전문가 검토안이다. 검토안이 생성되더라도 기존 공식 기획은 자동으로 변경되지 않는다. 사용자가 비교·검토하고 승인한 항목만 이후 공식 문서에 반영한다.
